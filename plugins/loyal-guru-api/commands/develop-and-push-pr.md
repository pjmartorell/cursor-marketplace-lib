name: develop-and-push-pr
description: Implement a Jira ticket end-to-end — branch, code, tests, commit, draft PR, CircleCI check, and staging label assignment. Use when the user asks to implement a ticket and push a PR.
---

Implement the specified Jira ticket or tickets. Create a new branch for these changes, with the following format: "PJM-" followed by the Jira ticket identifier (i.e CDP-10674) and followed by a descriptive feature name (full example: "PJM-CDP-10674-return-200-ok-empty-schema"). Ensure the branch is up to date with master branch. Run tests to ensure that your solution works properly and tests are updated. Then commit these changes into meaningful commits, except cached_results.yml which is generated by Rspec tests and we don't want to commit it. Then create a draft pull request according to the PR template (.github/pull_request_template.md). The PR title must follow this format, in example: [CDP-10674] My PR title. Ensure that CircleCI check passes for each of the branches or PRs involved (it's very important). Note that CircleCI takes 9 minutes approximately to run all tests. If tests pass in CircleCI, assign one of these labels by order of priority (deploy_staging, deploy_staging2, or deploy_staging3) to the PR, this will trigger the `.github/workflows/deploy.yml` workflow and deploy the branch in the specified staging server. Note that you must assign a staging label that is not already being used by another "open" PR (if all are already being used do not assign any label). Ensure the branch is up to date with master branch, otherwise the deployment is not fulfilled and the label must be re-applied to take effect.

In the PR description add a list of all the QA tests needed to test the fix/feature:
1. If it's testable from the frontend/owner, use the fetch-frontend-urls skill to find all affected frontend URLs from the loyal-guru-app-owner-v2 codebase. List the actual URLs and the steps needed to test them, along with the expected result.
2. If it's only testable as a direct API call, indicate which API calls need to be tested and what is the expected result.
3. Note that some code fixes may have implications in other components, so they should be tested too, but with less priority. If the logic to be tested has different if-else cases or some conditionals activated by feature flags, they should be tested too.
4. If the list of tests/steps is too long, make it collapsable with Markdown so it does not occupy so much space
